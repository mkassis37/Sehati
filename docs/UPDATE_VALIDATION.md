# اختبار تحديثات صحتي والاحتفاظ بالبيانات

## سلوك التحديث
- فحص GitHub Releases يعمل في نسخة Release، وليس في Debug.
- يقارن التطبيق versionCode، ويعرض release notes قبل التنزيل.
- ينزّل APK بواسطة Android DownloadManager.
- يتحقق من SHA-256 الوارد في update.json قبل استدعاء مثبت أندرويد.
- أندرويد يطلب موافقة المستخدم. لا يحاول التطبيق تجاوز شاشة التثبيت.

## شروط التحديث فوق النسخة الحالية
يجب أن تبقى قيمة applicationId وشهادة توقيع APK ثابتتين في كل إصدار. عند تحقق الشرطين، تثبيت APK كتحديث يحافظ على مساحة بيانات التطبيق وقاعدة Room ومفتاح SQLCipher في Android Keystore. لا تحذف التطبيق أثناء التحديث.

## نقطة مهمة حول نسخ Debug
نسخة Debug الحالية تضيف اللاحقة .debug إلى applicationId، بينما نسخة Release تستخدم applicationId الأساسي com.mkassis37.sehati. لذلك لا يمكن لنسخة Release أن تكون تحديثًا مباشرًا فوق Debug؛ يعتبرهما أندرويد تطبيقين منفصلين. قبل الانتقال لأول إصدار Release، صدّر نسخة صحتي الاحتياطية المشفرة وتحقق من إمكانية استعادتها في نسخة Release. بعد ذلك تتم التحديثات العادية دون إزالة التطبيق.

## اختبار الترقية المطلوب قبل النشر العام
1. تجهيز إصدار قديم Release بمفتاح التوقيع النهائي.
2. تثبيته على جهاز اختبار وإنشاء أكثر من ملف فردي وسجلات حساسية.
3. حفظ نسخة احتياطية مشفرة كإجراء احترازي.
4. نشر إصدار أحدث باستخدام المفتاح نفسه وversionCode أعلى.
5. تنزيله من داخل التطبيق وتثبيته فوق النسخة الموجودة، دون إلغاء التثبيت.
6. التحقق من ظهور كل الأفراد وسجلات الحساسية، وفتح القفل، وعمل النسخ الاحتياطي.
7. تكرار الاختبار على جهاز فعلي قبل اعتبار التحديث جاهزًا للمستخدمين.

لا يمكن إجراء اختبار ترقية APK موقّع فعليًا قبل تجهيز أسرار توقيع Release في GitHub. فحوص CI العادية تتحقق من البناء والاختبارات، لكنها لا تثبت تطابق شهادة التوقيع بين إصدارين.
